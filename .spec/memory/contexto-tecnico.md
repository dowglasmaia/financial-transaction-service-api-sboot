## As built in BE-03 (money integrity)
One conditional UPDATE enforces `balance >= amount` (`AccountJpaRepository.debit`, behind the port method `tryDebit`, used through `DebitAccountUseCase`). Deposit/withdraw/recharge = one `@Transactional` method; Pix = reserve (debit + `PENDING` ledger row) → MaiaBank → confirm/`COMPLETED` or compensate/`FAILED` (two short `TransactionTemplate` transactions, the remote call is never inside a transaction). Ledger has `status`; the statement counts only `COMPLETED`. Recharge event: `outbox_event` row written with the debit (through the `RechargeEventPublisher` port), `OutboxRelay` (`transaction.infrastructure.messaging`, every 1 s, at-least-once) publishes it to `recharge-mobile-topic` with the same JSON bytes and `__TypeId__` header. Flyway `V2`. Known gaps: no reconciliation of stuck `PENDING` Pix rows; relay has no `SKIP LOCKED`.

## Target design in one screen
* Each money operation = one `@Transactional` service method; debit via atomic conditional update (`WHERE balance >= :amt`) or `@Version`; ledger written in the same transaction.
* Pix: reserve (debit + ledger PENDING) → commit → call MaiaBank → confirm/compensate; Kafka via transactional outbox.
* [built in BE-04] the caller is resolved by `GetCurrentAccountUseCase` + the `CallerIdentity` port (`JwtCallerIdentityAdapter`); it resolves the Auth0 `sub` → `usuario.external_subject` → the single account. Unknown `sub` → 403. Authorization = role claim `https://financial-transaction/roles` (only `customer`, D-30); no scopes.
* Statement: account-scoped, half-open date range, paginated, totals by aggregate query, rows carry `id`.
* `GET /accounts/me`. Idempotency-Key on POSTs (store in DB) — built in SL-03 (`shared.idempotency`).
