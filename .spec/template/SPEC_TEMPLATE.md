# SPEC-<ID> — <Title>

| Field | Value |
|---|---|
| Status | Draft / Approved / In progress / Blocked / Done |
| Track · Wave | Backend or Frontend · Wave N |
| Depends on | SPEC-… (must be Done) |
| May run in parallel with | SPEC-… (only if files do not overlap) |
| Findings / decisions | F-xx, BR-xx, D-xx |
| Authorization | Approved by <who/when>. Approval of a document is **not** approval to implement (`shared/como-executar.md` §Before starting). |

## 1. Objective
One paragraph: the outcome and why.

## 2. Context to read first
`.spec/` documents and code locations the executor must read.

## 3. Scope
In scope / **Out of scope** (explicit).

## 4. Constraints and behaviour to preserve
KEEP rules that must not change; decisions that apply.

## 5. Tasks
Checkbox per task; tool/skill named when applicable. Mark only after verification and add an evidence line (format in `shared/como-executar.md`).

## 6. Acceptance criteria
Verifiable statements.

## 7. Mandatory verification
Commands/tests that must be executed (not only written).

## 8. Approval gates
Points where execution stops for a human (contract changes, behaviour changes, new dependencies).

## 9. Skills / tools
Which skill is used for which task.

## 10. Result summary (filled on completion)
Short result, validations, accepted limitations.
